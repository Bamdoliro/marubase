# 일회용 전화번호 인증 증명 (#441)

선행 PR: #442 → #443. 프론트 동시 변경이 필요한 호환성 변경입니다. DB 마이그레이션과 신규 환경 변수는 없습니다.

## 프론트 계약

1. POST /users/verification: 요청/응답 동일. phoneNumber와 type(SIGNUP / UPDATE_PASSWORD)을 전송합니다.
2. PATCH /users/verification: 기존 요청 유지. 성공 응답은 **204에서 200으로 변경**합니다.

```json
{
  "code": "OK",
  "message": "ok",
  "data": {
    "verificationToken": "<43자 URL-safe 랜덤 토큰>",
    "expiresIn": 300
  }
}
```

3. POST /users 및 PATCH /users/password: 기존 요청 필드에 verificationToken 필수 추가.
   각각 SIGNUP, UPDATE_PASSWORD로 확인한 증명만 사용할 수 있습니다.
4. 인증 토큰은 해당 화면의 메모리에만 보관하고 URL, 로그, 분석 이벤트, 영구 저장소에 넣지 않습니다.
   전화번호/용도 변경, 재발급, 완료, 만료 시 폐기합니다.
5. 기존 로그인 화면/일반 토큰 계약 변경은 선행 PR 문서를 참고합니다.

## 오류

| 상황 | HTTP | code | 프론트 처리 |
| --- | --- | --- | --- |
| 인증번호 1~4회 불일치 | 401 | VERIFICATION_CODE_MISMATCH | 재입력 안내 |
| 5번째 불일치로 폐기 | 429 | VERIFICATION_ATTEMPTS_EXCEEDED | 입력 중단 및 재발급 안내 |
| 미발급/만료/이미 사용/다른 전화번호·용도의 증명 | 401 | VERIFYING_HAS_FAILED | 인증부터 다시 진행 |
| 증명 누락/형식 오류 | 400 | 기존 validation 오류 | 요청 수정 |
| 요청 빈도 제한 | 429 | TOO_MANY_REQUESTS | 잠시 후 재시도; 위 폐기 오류와 구분 |

5회 폐기 이후 같은 인증번호를 다시 제출하면 VERIFYING_HAS_FAILED입니다.
인증 관련 401을 로그인 만료로 일괄 처리하지 말고 해당 화면에서 위 오류를 처리합니다.

## 원자성과 실패 처리

- OTP 비교/실패 횟수 증가/5회 폐기/증명 발급을 하나의 Redis Lua 실행으로 처리합니다.
- 성공한 OTP는 즉시 제거되어 같은 OTP로 증명을 반복 발급할 수 없습니다.
- 증명은 256비트 난수이고 Redis에는 HMAC-SHA256만 저장합니다.
- 전화번호·용도에 묶인 증명을 비교하고 삭제하는 작업도 하나의 Lua 실행입니다.
- 코드 및 증명은 각각 5분 TTL입니다. 재발급하면 이전 코드와 증명을 모두 무효화합니다.
- Redis 오류는 인증 성공으로 처리하지 않습니다. SMS 발송 오류는 해당 코드가 아직 현재 코드일 때 취소합니다.
- 증명 소비 후 DB 실패 또는 응답 유실 시 자동 재사용은 지원하지 않습니다. 다시 인증해야 합니다.
- Redis와 DB 사이에 분산 트랜잭션을 제공하지는 않습니다.

## 배포 및 검증

- verification:v2: 새 키 공간만 사용합니다. 기존 isVerified=true 기록으로의 호환 경로는 없습니다.
- 이전 서버와 새 서버를 섞지 말고 전체 인스턴스를 교체해야 합니다.
- 기존 진행 중 인증은 재발급해야 합니다. 프론트 연동 완료 전 단독 배포하지 마세요.
- 실제 Redis 테스트로 TTL, 전화번호/목적 구분, 재발급 무효화, 5회 폐기, 동시 발급·소비 시 단일 성공을 확인합니다.
